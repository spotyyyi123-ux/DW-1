## Explainable spam-enrichment: детекция признаков генеративного ИИ в письмах и кампаниях

## 0. Что именно требуется (перевод ТЗ на инженерный язык)

**Тип задачи:** детекция писем и кампаний с признаками генеративного ИИ + explainable
spam-enrichment.

**Прикладной финал:** модуль, который для аналитика SOC **объясняет, какие элементы
письма могли быть сгенерированы или модифицированы ИИ и насколько система уверена**.

**Ключевые сдвиги от «обычного детектора» — их легко упустить:**

| Наивная трактовка | Что требуется на самом деле |
|---|---|
| Бинарная классификация «текст ИИ / человек» | **Позлементное происхождение**: текст, тема, CTA, HTML, изображения, QR, ссылки, шаблон |
| Письмо как единица анализа | **Письмо + группа похожих сообщений = кампания** |
| Одна метрика качества | Precision/Recall/F1/ROC-AUC **+ полнота объяснений + устойчивость к маскировке** |
| Спам-корпус как негативы | **Легитимная корпоративная почта** как источник сложных false positives |
| Вердикт «фишинг» | **Enrichment**: дополняет существующий вердикт, а не подменяет его |

### Центральный тезис, который надо защитить

> **Происхождение ≠ злонамеренность.** Маркетинговый дайджест и HR-рассылка тоже
> написаны ИИ и тоже шаблонны. Поэтому система обязана держать **две независимые оси**:
> `ai_provenance` (стиль, генерация) и `intent` (намерение: запрос учётных данных,
> несоответствие ссылок, подмена бренда, репутация отправителя). Схлопывание их в один
> score — главная методологическая ошибка в этой задаче и главный источник false
> positives на корпоративной почте.

Это и есть научная новизна относительно Phish-Master / SpearBot / watermarking-работ.

## 1. Три оси постановки

```
ОСЬ 1 — СИГНАЛЫ        текст · тема · CTA · HTML · изображения · QR · ссылки · заголовки · шаблон
ОСЬ 2 — ПРОИСХОЖДЕНИЕ  human · ai_generated · ai_polished · template/kit · unknown   (+ уверенность)
ОСЬ 3 — МАСШТАБ        элемент → письмо → кампания (кластер)
```

**`ai_polished` — обязательный класс.** Реальный сценарий: атакующий пишет письмо сам,
потом просит LLM «исправить грамматику». Текст гибридный: тема — ИИ, тело — правленое
человеческое. Бинарная модель на таком ломается; позлементная — работает.
Именно поэтому в SemEval-2024 Task 8 есть отдельный сабтаск на **смешанный** текст.

## 2. Архитектура

```
ИНГЕСТ            .eml / .msg / IMAP / REST
   │
РАЗБОР MIME       headers | text/plain | text/html | inline-изображения | вложения | QR
   │              (+ опциональный рендер HTML в скриншот через headless chromium)
   │
ЭКСТРАКТОРЫ       параллельно, каждый со своей версией и кэшем по content-hash
   ├── text      : curvature-детекторы + стилометрия + мультиязычный энкодер
   ├── subject   : отдельная (короткая) ветка — мало текста, нужна агрегация с телом
   ├── cta       : извлечение императивов, интент-лексика, дедлайны, запрос креденшелов
   ├── html      : DOM-фингерпринт, обфускация, признаки генератора, ESP-маркеры
   ├── images    : спектральная/шумовая форензика, OCR, pHash, EXIF/размер
   ├── qr        : декодирование → URL → в ветку ссылок
   ├── links     : URL/домен, punycode/homoglyph, редиректы, репутация, mismatched anchor
   └── headers   : SPF/DKIM/DMARC, выравнивание From/Return-Path/Reply-To, mailer, Date/TZ
   │
ГРАФ ДОКАЗАТЕЛЬСТВ  каждое наблюдение → (элемент, сигнал, значение, вес, версия модели)
   │
ФУЗИЯ              ai_provenance(письмо) + intent(письмо)  ← ДВЕ РАЗНЫЕ ОСИ
   │              калибровка (isotonic/Platt), доверительные интервалы, отказ от ответа
   │
КАМПАНИИ           MinHash/SimHash LSH + эмбеддинги + HDBSCAN → кластер + скелет шаблона
   │
ОБЪЯСНЕНИЯ         атрибуция по элементам, подсветка спанов, faithfulness-проверка
   │
API                /v1/analyze · /v1/message/{id} · /v1/campaign/{id} · /v1/explain/{id}
   │
UI (SOC)           карточка enrichment: таблица элементов, подсветка, граф кампании, фидбек
```

**Инженерные обязательства:**
- Каждый экстрактор — независимый модуль с версией → без этого невозможны аблации
- Кэш по контент-хэшу части → один и тот же HTML в 10 письмах считается один раз
- Асинхронный инференс (arq/Celery). Тяжёлые детекторы (Binoculars) — только по требованию,
  с бюджетом времени на письмо
- Все доказательства хранятся (JSONB), а не только итоговый score: объяснение нельзя
  восстановить постфактум, его надо сохранять

## 3. Сигналы: что конкретно считать

### 3.1 Текст (тело)

| Метод | Что даёт | Стоимость | Оговорка |
|---|---|---|---|
| **Fast-DetectGPT** | условная кривизна вероятности за один проход | средняя | нужен скорер с логитами; калибровка EN не переносится на RU |
| **DetectGPT** | пертурбационная кривизна | высокая (много проходов) | использовать как эталон, не в проде |
| **Binoculars** | отношение perplexity / cross-perplexity (observer+performer) | высокая (2 модели) | сильный zero-shot; обязательна перекалибровка под язык |
| **Стилометрия** | burstiness, MTLD/TTR, профиль пунктуации, **частота опечаток**, сокращения | почти ноль | опечатки — неожиданно сильный признак: у ИИ их нет |
| **Классический ML** | TF-IDF (word+char n-grams) + CatBoost/LinearSVC | низкая | обучаемый бейзлайн, нужен для аблаций |
| **Мультиязычный энкодер** | xlm-roberta / ruRoberta-large / mDeBERTa | средняя | основной обучаемый детектор для RU+EN |

> **Мини-вклад, который стоит зафиксировать:** калибровка curvature-детекторов
> (Binoculars/DetectGPT) получена на английском. На русском пороги и ECE разъезжаются.
> Замер этого разрыва и перекалибровка по языкам — самостоятельный результат.

### 3.2 Тема письма

Короткий текст → самостоятельный детектор слаб. Работает как **признак в ансамбле**:
стиль, эмодзи, urgency-лексика, несоответствие `Re:`/`Fwd:` истории треда,
длина, наличие персонального обращения. Полезно: **несогласованность темы и тела** —
частая подпись гибридного происхождения.

### 3.3 CTA (call to action)

- Извлечение императивных конструкций и целевых действий
- Интент-лексика: «подтвердите», «обновите доступ», «в течение 24 часов»
- **Несоответствие текста ссылки и href** — один из сильнейших интент-признаков
- Лексическое разнообразие CTA **по кластеру**: у шаблона оно низкое, у LLM-генерации — выше

### 3.4 HTML — самый недооценённый сигнал

Три независимые группы признаков, которые надо **держать раздельно**:

**A. Признаки генератора (LLM писал HTML)**
- семантические теги, ровная вложенность, CSS-переменные, flex/grid
- аккуратные отступы, accessibility-атрибуты
- **отсутствие Outlook-хаков** (`<!--[if mso]>`, table-based layout) — реальные
  рассылки от ESP их почти всегда содержат

**B. Признаки вредоносности/обфускации**
- zero-width символы, плотность HTML-сущностей, разбиение слов комментариями
- base64-блобы, обфусцированный JS, скрытые блоки (`display:none`, белый на белом)
- форма с POST на внешний домен

**C. Признаки легитимного массового отправителя (гасители FP!)**
- трекинг-домены и joiner-параметры ESP (SendGrid / Mailchimp / Unisender / Salesforce)
- `List-Unsubscribe`, `Precedence: bulk`, корректный `Message-ID`-домен

### 3.5 Изображения

- **Форензика генерации**: спектральные пики в Фурье-области, шумовые остатки,
  артефакты JPEG-квантования, отсутствие EXIF при «фотографическом» виде,
  размеры, характерные для диффузионных моделей
- **CLIP-признаки** (подход UniversalFakeDetect) как обучаемый детектор
- OCR текста внутри картинки → в текстовую ветку (обход текстовых фильтров)
- **pHash** для склейки кампаний по одинаковым картинкам

### 3.6 QR-коды (quishing)

- Декодирование (pyzbar/opencv) → URL → обязательно в ветку ссылок
- Сам факт QR — интент-признак (обход почтовых сканеров ссылок)
- Различать сгенерированный QR и скриншот QR (артефакты масштабирования)

### 3.7 Ссылки

Длина/энтропия URL, глубина поддоменов, punycode и homoglyph-домены, TLD,
цепочки редиректов, **несоответствие anchor-текста**, репутация домена.
Отдельно — детектор легитимных трекеров, чтобы не считать корпоративную рассылку фишингом.

### 3.8 Заголовки

Результаты SPF/DKIM/DMARC, выравнивание `From` / `Return-Path` / `Reply-To`,
длина и аномалии цепочки `Received`, `X-Mailer`/`User-Agent` (скриптовая отправка),
несогласованность `Date` и таймзоны, формат `Message-ID`.
Классический ML (CatBoost) здесь работает лучше всего — много категориальных признаков.

### 3.9 Кампании и шаблоны

- **Near-duplicate**: SimHash/MinHash по нормализованному тексту + LSH
- **Структурная близость**: шинглы DOM, pHash картинок, набор ссылок
- **Семантическая близость**: мультиязычные эмбеддинги + HDBSCAN
- **Извлечение скелета шаблона**: общий каркас + переменные слоты. Классическая
  подпись фишинг-кита — жёсткий каркас с подстановкой бренда/ссылки/имени
- **Агрегация на уровень кластера**: если разброс слотов выглядит машинным, уверенность
  в ИИ-происхождении растёт (одиночное письмо могло быть написано человеком)

## 4. Модуль объяснений для SOC (ядро прикладного результата)

Аналитику нужен не score, а **ответ на вопрос «что мне проверить руками»**.

Карточка enrichment должна содержать:

1. **Сводка по аутентификации**: SPF/DKIM/DMARC, выравнивание отправителя
2. **Таблица происхождения по элементам**:
   `Тема · Тело · CTA · HTML · Изображение 1..n · QR · Ссылки` →
   `ai_provenance` + уверенность + короткое свидетельство
3. **Две отдельные шкалы**: `ai_provenance` и `intent` — визуально не смешивать
4. **Подсветка в теле письма**: спаны с наибольшей кривизной (у curvature-детекторов
   объяснение **встроенное**, а не post-hoc — это их преимущество перед чёрными ящиками)
5. **Структурные аномалии HTML** с указанием конкретных фрагментов
6. **Таблица ссылок** с флагом несоответствия anchor ↔ href и результатом декодирования QR
7. **Панель кампании**: участники кластера, скелет шаблона, подсвеченные переменные слоты
8. **Контр-свидетельства** — «почему уверенность не выше»:
   «есть joiner-параметры SendGrid», «DKIM выровнен», «опечатки в теле характерны для человека»
9. **Фидбек аналитика по каждому элементу** → активное обучение и рост датасета

> Пункт 8 — то, что отличает *enrichment* от *скорбора*. SOC-аналитик доверяет системе,
> которая явно показывает, чего она не знает.

## 5. Метрики

**Классические (по ТЗ):** precision, recall, F1, ROC-AUC — с разбивкой по типам элементов
и по языкам.

**Обязательные дополнительные:**

| Метрика | Как считать |
|---|---|
| **TPR@FPR=1% / 0.1%** | рабочие точки SOC, а не порог 0.5; bootstrap-CI по письмам |
| **Калибровка** | ECE, reliability curves — уверенность ≠ точность ломает доверие |
| **Полнота объяснений — faithfulness** | ERASER-подход: *comprehensiveness* (убрали подсвеченное → score должен упасть) и *sufficiency* (оставили только подсвеченное → score сохраняется) |
| **Согласованность объяснений** | совпадение подсветки с человеческой разметкой рациональностей (token-F1) |
| **Устойчивость к маскировке** | TPR@FPR как функция силы атаки (см. §6) |
| **False positives на легит-почте** | FPR на отдельном корпоративном наборе при рабочей точке |
| **Качество кластеризации** | BCubed F1, ARI, homogeneity/completeness |
| **Извлечение шаблона** | точность определения общих/переменных слотов |
| **Стоимость** | латентность p50/p95 и токены на письмо — для SOC критично |

**Аблации (обязательны):** только текст · только структура (HTML/ссылки/заголовки) ·
только изображения+QR · без curvature · без стилометрии · полная фузия · без кластеризации.
Таблица аблаций — половина ценности отчёта.

## 6. Устойчивость к маскировке AI-признаков

Набор атак (по возрастанию силы), для каждой — кривая деградации:

| Атака | Что ломает |
|---|---|
| LLM-перефраз | curvature-детекторы и watermark |
| Обратный перевод (RU→EN→RU) | стилометрию и водяные знаки |
| Синонимическая замена, перестановка предложений | кривизну |
| Внесение опечаток и «человеческого шума» | признак отсутствия опечаток |
| Zero-width символы, гомоглифы | токенизацию и признаки обфускации |
| Разбиение/склейка предложений | burstiness |
| **Watermark spoofing** | ложные срабатывания watermark-детектора |

Отдельный вывод: **структурные и интент-признаки (HTML-каркас, ссылки, заголовки,
QR, шаблон кампании) маскировать почти невозможно** — они не про стиль.
Это ключевой аргумент архитектуры: стилевые сигналы дают покрытие, структурные —
устойчивость.

## 7. Легитимная корпоративная почта как hard negatives

Это не «фон», а **отдельный эксперимент**, потому что такая почта одновременно:
массовая, шаблонная, **и частично написана ИИ** (маркетинг, HR-рассылки, авто-ответы).

Что нужно:
1. Отдельный размеченный набор (внутренние образцы Doctor Web + публичные рассылки)
2. Разделение ошибок: `FP-стиль` (модель путает AI-маркетинг с AI-фишингом) и
   `FP-интент` (ложная интерпретация намерения) — разные причины, разные фиксы
3. Признаки-гасители: ESP-трекеры, `List-Unsubscribe`, выровненный DKIM, история домена
4. Отчёт: **FPR именно на этом наборе** при рабочей точке, отдельно от общего FPR

> Вывод, который стоит защищать: система, которая на корпоративном дайджесте кричит
> «AI-generated!», бесполезна в SOC — формально она права, практически вредна.

## 8. Данные и бенчмарк

**Тексты / AI-детекция:**
- **SemEval-2024 Task 8** — multilingual machine-generated text detection; есть сабтаск
  на **смешанный** human-machine текст, прямо в нашу задачу
- **M4 / M4GT** — multi-lingual, multi-domain, multi-generator
- **HC3**, **RAID** (RAID содержит состязательные атаки — под §6)
- **RuATD** (Dialogue-2022) — русскоязычная детекция искусственных текстов
- **MULTITuDE** — мультиязычный бенчмарк (проверить актуальность и лицензию)

**Фишинг / спам:**
- Nazario, PhishTank, OpenPhish, SpamAssassin, CEAS 2008, TREC Spam, Enron
- Русскоязычные корпуса — проверять доступность и лицензии отдельно

**Изображения:**
- GenImage, CIFAKE — для ветки форензики

**Внутренние:** образцы Doctor Web — только локальная обработка (см. §9).

⚠️ Все перечисленные наборы **проверить на лицензию и актуальность** перед использованием.
Названия — кандидаты из литературы, а не гарантированно доступные датасеты.

## 9. Безопасность и приватность (критично для индустриального проекта)

- **Внутренние образцы Doctor Web не покидают контур.** Никаких облачных API на них:
  GPTZero и подобные закрытые сервисы — **только на публичном бенчмарке, для сравнения**
  («как коммерческий детектор справляется с открытыми данными»), никогда на внутренних письмах
- Персональные данные в письмах: маскирование перед логированием, отдельное хранение
- Логи с полным телом письма — только в защищённом хранилище, с TTL
- Раздел **ethics / dual-use** в отчёте: мы детектируем, но тот же корпус пригоден
  для генерации. Явно оговорить, что генерация фишинга для обучения делается на
  синтетических получателях
- Отдельно: атака `watermark spoofing` — детектор не должен быть оружием против невиновных

## 10. Стек и почему именно он

| Слой | Выбор | Обоснование |
|---|---|---|
| Скореры | `transformers` + Qwen2.5 / Gemma / mGPT | нужны логиты; **мультиязычность обязательна** (RU+EN) |
| Детекторы | Fast-DetectGPT, Binoculars (эталон), GPTZero (внешний бейзлайн) | покрывают спектр «дёшево → точно → коммерчески» |
| Классический ML | **CatBoost** + LightGBM | много категориальных признаков (заголовки, домены, ESP) |
| Признаки | scikit-learn, `tldextract`, `dnspython`, `beautifulsoup4`/`lxml` | HTML и ссылки |
| Изображения | OpenCV, `pyzbar`, Pillow, CLIP | форензика, OCR, QR, pHash |
| Кластеризация | `datasketch` (MinHash/LSH), `sentence-transformers`, HDBSCAN | near-dup + семантика |
| Explainability | SHAP (TreeSHAP), Captum (IG), attention rollout | разные методы под разные модели |
| Backend | FastAPI + Pydantic v2, Postgres + JSONB, Alembic, arq/Celery | асинхронный инференс |

## 12. Риски и как их снимать

| Риск | Снятие |
|---|---|
| Утечка данных при сплите | Сплит по шаблонам/кампаниям, не по строкам; проверка near-duplicate |
| Спуриозные стилевые признаки | Кросс-генераторный тест + **de-styling контроль** (нижний регистр, нормализация пунктуации, снятие форматирования) |
| RU-калибровка curvature-детекторов | Явный замер ECE по языкам, перекалибровка, честный отчёт о разнице |
| Тяжёлые детекторы в проде | Binoculars — только офлайн-эталон; в проде Fast-DetectGPT + энкодер |
| FP на корпоративной почте | Отдельный набор + признаки-гасители + две раздельные оси |
| Объяснения «на словах» | Только метрики faithfulness, а не демонстрация одной красивой картинки |
| Цифры в отчёте набраны руками | Все таблицы генерируются из сохранённых предсказаний, `make eval` |

## 13. Чего не делать

- Не схлопывать `ai_provenance` и `intent` в один score — это ломает весь замысел
- Не начинать с UI: сначала API и заглушка evidence
- Не гонять облачные детекторы (GPTZero) на внутренних образцах
- Не отчитываться одной accuracy
- Не ставить Binoculars в прод-путь
- Не показывать объяснение, не измерив его достоверность
- Не рисовать графики руками

## 15. Формулировка вклада для защиты

> Мы показываем, что детекция AI-assisted фишинга не сводится к бинарной классификации
> «текст написан ИИ». Предлагается позлементная модель происхождения (тема, тело, CTA,
> HTML, изображения, QR, ссылки) с явным разделением **происхождения** и **намерения**,
> агрегируемая до уровня кампании через кластеризацию и извлечение скелета шаблона.
> Система даёт аналитику SOC объяснение с измеримой достоверностью (comprehensiveness /
> sufficiency), устойчива к маскировке стилевых признаков за счёт структурной ветви
> и отдельно оценивается на легитимной корпоративной почте как источнике сложных
> false positives — где стилевые детекторы принципиально ненадёжны.
