# TEAM.md — Роли, распределение задач и регламент DW-1

> Директива «мозга»: кто, что, в каком порядке и как отчитывается.
> ТЗ (что реализовать) — `docs/SPEC.md`. Краткая версия для агентов — `AGENTS.md`.

## 1. Участники и их роли

| Роль | Кто | Функция |
|---|---|---|
| Наставник («мозг») | ты + твой DSH-агент | задаёт цели, распределяет задачи, ревьюит MR, мёржит, решает блокеры и лицензионные вопросы |
| Подопечный | человек из команды | владелец воркстрима: ставит задачи своему агенту, проверяет его работу, доводит до DoD |
| Агент подопечного | DSH-агент у подопечного | выполняет механическую и инженерную работу по задачам воркстрима |

Пара «подопечный + его агент» — минимальная рабочая единица. Подопечный **не пишет код руками
в одиночку**: он направляет агента, проверяет артефакты и несёт ответственность за результат.

## 3. Матрица распределения (зависит от числа подопечных)

### 3 подопечных (базовый вариант)
- **A** = W1 + W4 (данные → фузия: владеет сквозным пайплайном)
- **B** = W2 (текстовые детекторы)
- **C** = W3 + W5 (структура + объяснимость/UI)

### 4 подопечных
- A = W1, B = W2, C = W3, D = W4 + W5.

### 5 подопечных (полный вариант)
- A = W1, B = W2, C = W3, D = W4, E = W5.

### 2 подопечных
- A = W1 + W2, B = W3 + W4 + W5. Вехи M6–M7 сдвигаются; приоритет — M0–M5 и отчёт.

## 4. Порядок запуска (первые 10 рабочих дней)

| День | Событие |
|---|---|
| 1 | Наставник клонирует репозиторий на `D:\dw1`; подопечные получают доступ; каждый поднимает DSH, кладёт `AGENTS.md` в корень своего клона и даёт агенту прочитать `docs/SPEC.md` + свой раздел TEAM.md |
| 1–2 | **M0 всеми вместе**: A собирает скелет репозитория и ingest, B/C ставят заглушки своих экстракторов. Цель дня 3: `make demo` работает |
| 2–4 | W1 качает стартовый набор на D: (порциями), заполняет datasheet; остальные пишут настоящие экстракторы на заглушечных фикстурах |
| 5–6 | W1 отдаёт бейзлайн-скрипт; W2 готовит внешний контур (Colab-ноутбук Fast-DetectGPT на публичной выборке); W3 собирает признаки структуры |
| 7–9 | Первый общий `make eval`: все ветки считаются на едином сплите, метрики в одну таблицу |
| 10 | Промежуточная демо-защита: карточка enrichment на 3 примерах + таблица аблаций v0 |

## 5. Регламент недели

- **Понедельник**: наставник ставит цели недели (issues в трекере, по одному на задачу; в каждом
  issue — определение готовности из SPEC §10).
- **Среда**: подопечный показывает агенту инкремент; подопечный докладывает блокеры наставнику.
- **Пятница**: общий прогон `make eval`; подопечные присылают MR; наставник мёржит, обновляет
  `docs/notes/week-NN.md` (что сделано, какие цифры, какие решения).

## 6. Правила для агентов подопечных (дублируются в их AGENTS.md)

1. Работать только в своём воркстриме; чужие модули не править без issue-согласования.
2. Читать контракты (§4 SPEC) перед кодом: Evidence JSON v1 — закон; его нарушение ломает общий eval.
3. Каждый MR: код + тесты + метрики из `make eval` + лицензия данных. Без метрик MR не ревьюится.
4. Внутренние данные заказчика — только локально; облачные API — только публичные данные.
5. Не выдумывать результаты; не подгонять пороги под тест; всё воспроизводимо из `make eval`.
6. Долгие прогоны — фоновые задачи; не блокировать сессию ожиданием.
7. Все новые источники литературы — в `docs/lit.md` через dsh-cite; все новые данные — в datasheet.

## 7. Коммуникация и артефакты

- Трекер задач: issues в git-репозитории `D:\dw1` (теги `w1`–`w5`, `blocker`, `m0`–`m8`).
- Еженедельные заметки: `docs/notes/week-NN.md` (ведёт наставник, дополняют подопечные).
- Все таблицы и графики в отчётах — из `data/runs/`; «красивые» картинки делаются только
  поверх реальных артефактов.
- Спор о метрике решается её воспроизведением: кто-то из пары перезапускает `make eval` с тем же
  `run_id`-конфигом; расхождение — баг, чинится до совпадения.

## 8. Критерии готовности подопечного (к защите)

1. Его модули проходят все вехи его воркстрима (SPEC §7).
2. Его ветка даёт измеряемый вклад минимум в одну аблацию (SPEC §8).
3. Он может за 10 минут объяснить: что его модуль считает, где его слабость, и показать
   faithfulness-метрику своего объяснения.
4. Его код прошёл ревью наставника без «разобраться позже».

## 9. Что НЕ делегируется подопечным

- Финальная формулировка вклада и позиционирование против литературы (docs/lit.md §5).
- Решения по лицензиям внутренних и спорных данных.
- Изменение контракта Evidence JSON v1 и структуры репозитория.
- Мёрж в main и релизы отчётов.

## 10. Git-протокол (обязателен с M0)

- Один репозиторий `D:\dw1`; ветки по воркстримам: `w1/<task-slug>`, `w2/<task-slug>` и т.д.
  Прямые коммиты в `main` запрещены всем, включая наставника.
- Формат коммита: `<scope>: <что>` (scope: `ingest | extract | model | campaign | explain |
  api | eval | data | docs | ci`). Пример: `extract: html-фичи группы A (mso-хаки)`.
- MR: заголовок + чеклист DoD (SPEC §10); ревью подопечного → мёрж наставником (squash).
- Теги вех `m0`…`m8`. Сломанный `main` — стоп проекта: чинится до продолжения.
- `data/raw/`, `data/runs/`, `reports/` — вне git (`.gitignore`); `datasheet.csv` и
  `splits.yaml` — в git.
- После каждого мёржа `make test` и `scripts/smoke.py` должны проходить.
